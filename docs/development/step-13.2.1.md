## Step 13.2.1：向聴数と有効牌によるCPU通常打牌
> **歴史資料:** 以下は整理前READMEのStep記録です。実施当時の仕様・未実装項目・検証結果を示し、現在の仕様を表すものではありません。現在の仕様は [SPEC](../SPEC.md)、実装状況は [ROADMAP](../ROADMAP.md) を参照してください。

`calculateShanten(tiles)` は門前13枚を入力とする純粋関数です。テンパイは0向聴、テンパイまであと1段階は1向聴です。一般形・七対子・国士無双を個別に返し、その最小値を手牌全体の向聴数とします。枚数違い、不正な牌、同種5枚以上を拒否し、入力を変更しません。既存の `Tile` / `TILE_KINDS` / `tileKindKey()` を使用し、赤5と通常5は同種です。

一般形は34種の枚数配列を3色と字牌に分け、刻子・順子・雀頭・対子搭子・隣接搭子（両面/辺張）・1枚間隔搭子（嵌張）・孤立牌の**すべての分解候補**を探索します。各部分を面子数・搭子数・雀頭有無の組に集約して組み合わせ、`8 − 2×面子数 − min(搭子数, 4−面子数) − 雀頭有無` の最小値を取ります。重複する順子/刻子や雀頭候補も探索します。面子4組・雀頭1組の上限と搭子上限で枝を制限します。七対子は `6 − 対子種類数 + max(0, 7−異なる牌種数)`、国士無双は `13 − 么九字牌の種類数 − 対子有無` です。同種4枚は七対子の対子1種類です。

CPUは所有する14枚の**物理ID**を候補として、打牌後の13枚を評価します。比較順は、①最小向聴数が小さい、②有効牌の見込み残り枚数が多い、③有効牌種類数が多い、④赤5を捨てない、⑤物理ID昇順です。同一入力の結果は固定で、最終同点に乱数を使いません。同種の打牌評価を共用しても物理IDと赤牌属性は保持します。

有効牌は、仮想ツモ後に最適な次の打牌を行うことで向聴数が減る牌種です。0向聴の場合は既存 `isWinningShape()` で和了形を完成する牌種を調べます。打牌後に既に4枚ある牌種の仮想5枚目は除外します。各有効牌の見込み枚数は4枚から**自分の手牌＋ツモ牌、4人の河、公開ドラ表示牌**を引きます。候補の打牌は河に移っても見えるので、元の14枚を差し引いたままです。赤5と通常5は合算し、物理IDを重複カウントしません。公開済み4枚により残り0枚の有効牌も種類として区別し、見込み枚数には0を加えます。理論上0向聴でも実際の和了牌が残っていない場合があり、向聴数と実際の待ち・リーチ成立条件を混同しません。

戦略の純粋関数には自分の14枚と公開牌だけを渡します。他家の手牌、未公開の生きた牌山の配列、非公開の王牌、実際の次ツモは参照しません。公開ドラを取り出す既存関数だけを境界で呼びます。非公開牌の交換や牌山の並べ替えでも選択が変わらないことをテストしています。

自動進行の優先順位は **ツモ和了 → リーチ成立済みならツモ切り → 既存条件を満たすリーチ → 向聴数戦略の通常打牌** です。リーチ候補の「待ち種類数最大→物理ID順」は変更していません。`chooseRandomDiscard()` と `AutomaticTurnOptions.chooseDiscard(player, random)` は維持しています。旧ランダム挙動・旧マイクロタスク待機を検証するテストは明示注入で継続します。フリテン、リーチ保留、供託確定、ロン・ツモ・得点・局進行・点棒保存則の処理とUI/CSSは変更していません。

### 計算量・性能記録

34要素の枚数配列で探索し、同じ牌構成と部分分解を1手のローカルキャッシュでメモ化します。異なる物理牌でも同種打牌は1回だけ評価し、最小向聴数を達成しない候補の有効牌探索を省きます。仮想ツモのツモ切りは改善しないので次打牌探索から除外します。キャッシュは手番を越えて保持しません。自動進行は約6msの区間ごと（仮想ツモ評価の境界）に `setTimeout(0)` で制御を返します。各区間は不可分な探索の分だけ予算を超える可能性があります。計算中にDOMを更新せず、既存300ms待機を維持し、再開時にキャンセル/世代/状態変更を検査して古い計算を確定しません。

Linux / Node v24.19.0、120種類の合法な通常配牌、20手ウォームアップ後の計測（ms）。単一時間閾値によるテストにはしていません。

| 対象 | 平均 | 中央値 | 最大 |
| --- | ---: | ---: | ---: |
| 13枚向聴数 | 0.038 | 0.029 | 0.462 |
| 14枚の候補向聴数のみ | 0.101 | 0.078 | 1.205 |
| 有効牌込み選択 | 8.967 | 7.519 | 44.781 |
| Chromium 13枚向聴数 | 0.045 | 0.000 | 0.700 |
| Chromium 有効牌込み選択 | 5.748 | 5.600 | 13.800 |

Chromiumの中央値0は計時分解能によります。Nodeのキャッシュは平均1,661エントリ、中央値1,659、最大3,121、Chromiumでは平均1,639、最大3,121です（手牌結果＋部分分解のエントリ数、ヒープバイト数ではありません）。重複分解が多い `11122233344455m` 等4種類も確認し、初回含め約6〜18msでした。詳細は [`docs/step13.2.1/benchmark.json`](../../docs/step13.2.1/benchmark.json)、[`chromium-benchmark.json`](../../docs/screenshots/step13.2.1/chromium-benchmark.json) にあります。

実際の3CPU連続手番は300ms×3の待機を含め概ね0.95〜1.24秒でした。描画フレームを継続して記録しています。ブラウザ回帰を併走した環境で50ms超のフレーム/long taskも観測したため、「全処理で引っかかりがない」とは断定しません。通常手番のフレーム最大値は約50〜133ms、画面描画・既存和了判定等も含むlong taskは約50〜98msでした。向聴数選択単体の計測と実動作を併記しています。iPhone Safariでの速度は未計測です。

再計測：`node tests/benchmark-shanten.ts`。ブラウザ：`npm run dev -- --host 127.0.0.1 --port 4173` を起動し、Playwright PythonとChromiumのある環境で `python tests/browser-shanten.py`。依存ライブラリは追加していません。

### 固定牌山・通常配牌の再現手順

合法な136枚固定牌山の自動テスト `tests/shanten-progression.test.ts` は、CPU1の `123m 11z 23p 45s 67s 2z 3z`（2向聴）に `4p` をツモって通常打牌後1向聴、次の `3s` で0向聴に到達し、既存のリーチ処理が宣言するシナリオです。1,000点徴収・宣言牌ID・次手ツモ切り・136枚の同一物理IDと点棒100,000点を検証します。

通常配牌はLCGの固定シード0（`tests/helpers.ts` の `seeded(0)`）で再現できます。本番へ固定シードや状態注入UIを追加していません。ブラウザテストの通信差し替えだけで `startGame(seeded(0))` を使い、通常の戦略と300ms待機を実行します。

1. 自分のツモ牌を選び「打牌する」を押すことを繰り返します（ロン可能時は「見逃す」）。
2. 初期CPU1/2/3はそれぞれ3/3/5向聴。CPU1は通常打牌1回目で2向聴、5回目で1向聴、8回目でテンパイ・リーチ、24,000点・供託1本になります。
3. CPU1の次手はツモ切り。CPU2も9回目でリーチし、供託2本になります。その後の人間打牌でCPU2のロンが成立し結果ダイアログが開きます。
4. 初期・通常打牌後・自然なリーチ・和了結果の7サイズ画像は [`docs/screenshots/step13.2.1/`](../../docs/screenshots/step13.2.1/) に保存しています。

通常配牌8シード（0〜7）で新旧戦略を比較しました。新戦略は各シードで1〜2CPUがテンパイ・リーチし、ランダム戦略はこの8シードではテンパイ/リーチ0でした。CPU3の自然なリーチもシード1/3/4/7で確認しています。これは固定シードでの検証結果であり、全対局でリーチを保証する仕様ではありません。比較は同じ配牌・同じ人間ツモ切り方針ですが、CPU打牌が変わるため局の終了時点や獲得ツモは変わり得ます。席ごとの向聴数推移・最小向聴数・テンパイ/リーチ席はbenchmark.jsonに記録しています。
