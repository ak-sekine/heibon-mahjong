### 各機能に関係する現行仕様

- **和了候補:** `evaluateWin()`が役・候補・点数・支払者別金額を作る。`getRonCandidates()`は和了形、役、フリテンを各席ごとに判定する。`resolveRonDeclarations()`は選ばれた候補だけを一度に確定する。
- **役満:** 現行12種類（基本役満8種類、天和・地和等の追加を含む）を1種類につき1役満とする。異なる役満は同一候補内で加算する。役満にはドラを加えない。`calculateScore()`は役満数を扱えるので、役満数の倍増自体は可能だが、特殊待ちの見分けと候補情報・表示は未実装。
- **ロン:** 現在は頭ハネではなく、複数人のロンが同時成立する。ロン支払いは各和了者ごとに放銃者1人が負担する。本場300点は和了者ごと、供託は放銃者から席順で近い和了者1人が一括取得する。
- **流局:** Issue #18の確定動作では九種九牌・四風連打・四家立直・四開槓は各設定ON時に途中流局し、罰符なし、点棒移動なし、供託持越し、親維持、本場+1。局数は進まず、これらの途中流局だけではオーラス終了にならない。
- **CPU:** オフラインとオンラインWorkerは共通のゲーム・役・精算関数を使う。CPUは合法なロン候補を自動で宣言する。オンラインはサーバーがCPU判断と人間全員のロン回答を集約してから解決する。
- **ルール保存:** `src/model/rules.ts`の`GameRules` schema v4、localStorage version 4。Workerは作成時ルールをDBに保存し、対局セッション全体をJSONで永続化する。再接続時に同セッションをhydrateする。追加設定を採用するならschemaを上げ、旧schemaは今回の項目OFF／現行動作となる既定値へ正規化する必要がある。

### Issue #18との整合

Issue #18の実装では、ロン宣言がなければ四風連打等を確認して途中流局にします。三家和はロン宣言窓を閉じた後にだけ判定し、**採用する場合は三人が実際にロンを宣言したときだけ**流局とするのが整合的です。単なるロン候補数では判定しません。

Issue #18の既存処理に三家和を新しい`abortiveDraw`理由として渡せば、現在の途中流局精算（罰符・通常点移動なし、供託持越し、親維持、本場+1、局数据置）が再利用できる。通常流局やIssue #18の個別ON/OFFに混ぜず、独立設定とする。四風連打と三家和が同じ4枚目の第一打で同時に候補になった場合は、ロン回答を閉じた後、実宣言3名なら三家和を先に確定する仕様を推奨する。現状どちらも成立しうる優先順位は未定義。

**精算例（推奨方式、親・子各1役満、2本場、供託なし）**

- **子が大三元ツモ:** 親・他の子2人なら通常 `16,000 + 8,000 + 8,000 = 32,000` 点。責任者が全32,000点を支払い、本場分600点も3人払いの代わりに責任者が負担するなら合計32,600点。本文の推奨では本場は独立して通常ツモ精算するため、責任者が役満32,000点、3人が各200点を払う（責任者は合計32,200点）。
- **親が大三元ツモ:** 通常は子3人が各16,000点、合計48,000点。パオなら責任者1人が役満分48,000点を払い、2本場の600点は推奨案では各支払者が200点ずつ通常精算する。
- **子が大三元ロン、責任者と別の子Cからロン:** 役満32,000点を責任者とCが16,000点ずつ。2本場600点は現行ロン規則どおりCが支払い、Cは合計16,600点、責任者は16,000点。Cが親なら点数額は同じ配分基準を適用するか、親の通常役満48,000点に対して折半24,000点ずつとする。親和了のときはロン額48,000点なので各24,000点。
- **複合役満:** 子の大三元＋字一色が各1役満なら総額64,000点。大三元分の32,000点だけを責任者へ割り当てる。ツモなら字一色分32,000点は通常（親16,000、子各8,000）。別人ロンなら責任大三元分は責任者／放銃者16,000点ずつ、字一色分32,000点は放銃者。2本場は既存の1和了分だけ加える。
- **供託:** 供託2本なら和了側へ2,000点。パオがあっても二重に移動させない。ロン複数時の取得席は現行規則のまま。

例中の本場と複合役満の責任範囲は推奨する一案であり、公開ルールの共通必須仕様ではない。親・子を入れ替えた場合の点数、同じ責任者が複数役満に関わる場合、他の和了者が同じ捨て牌でロンする場合も採用前にテーブル化する。

**推奨理由:** よく知られた2役へ限定し、牌を鳴かせた責任という利用者が追いやすい原因を記録する。役満ごとの責任額分離で既存の「異なる役満を複合する」仕様を壊さない。パオ全体は単純な点数係数の変更ではなく責任者記録・複数支払者対応を要するため規模大。

### 実装差分・依存・リスク

1. **人和:** `WinningContext`または和了候補に「子の初回自摸前・局内鳴きなし」を表す検証済みの由来を渡す。ロン候補を作る際、通常役候補と独立した固定満貫候補を比較し、高い方を一度だけ採る。フリテン・合法形・ロン窓は現行`getRonCandidates()`の入口で維持する。人和成立には通常役なしでも固定満貫で和了可能にする必要があり、`analysis.hasSupportedYaku`条件の単純な緩和は通常ロンの「役なし不可」を壊す危険がある。初回はオフライン・CPU・オンラインの共通関数を用い、オンラインに独自点数判定を持たせない。
2. **パオ:** 副露/槓成立時に大三元・大四喜・四槓子それぞれの責任者を局状態へ固定する。最終ロン/ツモ時点から逆算するだけでは、同一役の最後の必要刻子と責任した席が失われ得る。和了候補に役満別カウントと責任seatを保持し、支払内訳を複数payerへ分ける。`settleRound()`の「ロンpayer=放銃者」検証を、対象役満分に限る二者payerへ置換し、本場・供託は役満責任額に混ぜず確定仕様どおり処理する。`assertPointConservation()`を維持する。**最大規模・最大リスク**は役満別配賦、点棒端数、責任者=放銃者の重複payerとsession復元。
3. **特殊形ダブル役満:** 役名ごとの`yakuman`数を設定で調整する。四暗刻単騎は既存`candidate.wait === 'tanki'`、国士十三面は和了牌を除いた直前13枚が全13種1枚ずつか、純正九蓮は直前13枚が同一色の`1112345678999`かを判定する。4種を一つの設定に結び、OFFなら全件を1へ戻す。異なる役満の和は維持し、他役満との複合は倍化しない。大四喜2個分をパオ配賦するためパオと本機能は依存する。
4. **複数ロン・三家和:** ルールに独立booleanを追加する。回答完了後に`yes`集合を作り、(a) 3人全宣言かつ三家和ONならabortive draw、(b)複数ロンONなら宣言者全員和了、(c)OFFなら候補の座席優先順で1人だけ和了、の順で決める。三家和成立時は`winResult`を作らず新しいabortive reasonを#18の`settleRound()`へ渡す。槍槓にも同じ判定を適用し、窓を閉じる前に槓を成立させない。オンラインはサーバーが全回答後にのみ一度確定。`GameRules`を拡張し、localStorage、ホスト部屋snapshot、再接続・次局・再戦、設定UI・読み取り専用表示へ同じ値を伝播する。

### ユーザー確定仕様

#### 人和

- ON/OFF、初期値OFF。
- 子の第一自摸前で、局内に鳴きがない状態で成立した有効ロン。
- 固定満貫。人和を他役の翻数へ加算しない。
- 通常役の得点が人和固定満貫を上回る場合は通常役の高い得点を採用。
- フリテン等、通常ロン制約を適用。

#### パオ（責任払い）

- ON/OFF、初期値OFF。対象は大三元・大四喜・四槓子。
- 大三元／大四喜を確定させる鳴きを許した打ち手を責任者とする。
- 四槓子は4つ目の槓が大明槓である場合だけ責任成立。責任者はその大明槓に使った牌の打ち手。暗槓・加槓では成立しない。実際に四槓子で和了した場合だけ責任払いを適用。
- ツモでは責任者がパオ対象役満分を全額負担。ロンでは対象役満分を責任者と放銃者で折半。責任者と放銃者が同一なら、その人が対象役満分を全額負担。
- 複合役満ではパオ対象役満分だけ責任払いし、他役満分は通常精算。
- 本場はツモでは責任者、ロンでは放銃者が負担。供託は通常処理。
- 大四喜がダブル役満なら2倍分をパオ対象とする。ダブル役満の本場特例は採用しない。

#### 特殊形ダブル役満

- 4種類一括のON/OFF、初期値OFF。
- 四暗刻単騎、国士無双十三面待ち、純正九蓮宝燈、大四喜が対象。
- ONなら各2倍役満、OFFなら各1倍役満。他の異なる役満との複合加算を維持。

#### 複数ロン・三家和

- 独立した2設定。複数ロンは初期値ON、三家和流局は初期値OFF。

| 複数ロン | 三家和流局 | 2人ロン | 3人ロン |
| --- | --- | --- | --- |
| OFF | OFF | 頭ハネ | 頭ハネ |
| OFF | ON | 頭ハネ | 三家和流局 |
| ON | OFF | 2人和了 | 3人和了 |
| ON | ON | 2人和了 | 三家和流局 |

- 頭ハネは放銃者の下家→対面→上家の順で、宣言済みの有効ロンから1人を選ぶ。
- 三家和流局は同一ロン窓で3人全員の有効宣言が確認された場合だけ成立。槍槓も通常ロンと同じ判定を使い、別の三家和設定は設けない。
- 三家和は点棒移動なし、親維持、本場+1、局数据置、既存供託を持ち越す。最終局等の終了処理はIssue #18の途中流局処理に揃える。
- 宣言受付完了前に和了・流局を確定しない。オンラインではWorkerが最終判定する。
- 四風連打が成立する打牌に有効ロンがあればロンを優先。
- リーチ宣言牌に3人がロンし三家和流局となる場合、宣言リーチを不成立にして宣言者の1,000点を供託しない。既存供託は持ち越す。
- 頭ハネで対象外になった宣言者のフリテンは、局が終了するので追加の独立仕様項目にしない。
- 槍槓ではロン回答が終わるまで槓を確定しない処理順を実装時に確認する。

### 公式ルールと独自仕様

第一参照資料は日本プロ麻雀連盟公式サイトの[「～2024年度」ルール解説](https://www.ma-jan.or.jp/column_other/115081.html)。本文の「役満のパオ」欄で、大三元・大四喜・四槓子の対象、ツモ全額、ロン放銃者との折半を確認した。同欄は通常の積み場は放銃者負担、ダブル役満時に積み場の別扱いも記載する。本ゲームの本場ルール（ツモ時責任者負担、ロン時放銃者負担、ダブル役満の別特例なし）はユーザー決定による独自仕様で、同資料と区別する。

この資料で四槓子の4つ目を大明槓に限定する条件、責任記録の正確なタイミングまでは確認できない。人和、特殊形4種を一括設定する方式、複数ロン／三家和の本ゲーム設定や初期値も本ゲーム独自の採用仕様として記録し、連盟規定に書かれているとは主張しない。取得できた資料は「～2024年度」と示されたもので、2026年度の現行競技規定全条文を確認した意味ではない。

先行記録に挙がる協会、麻雀格闘倶楽部、WRC資料は、リンクの存在と本文を今回確認したことを分ける。今回、それらを連盟ルールの裏付けとして扱っていない。

### 既存コードとの差分・処理設計

- **役・点数:** `analyzeYaku()`は現在四暗刻単騎、大四喜、国士13面、純正九蓮を2倍にせず、役満種類を候補上で加算する。`calculateScore()`は役満数×8,000基本点を親子・ロン/ツモ別に算出する。特殊形は和了直前の13枚を検査する判定と役ごとの倍率が必要。
- **人和・初巡:** `evaluateWin()`は現在役なし候補を無効にし、人和専用の成立理由・満貫候補を持たない。`callsMade`、`kanCount`、河、副露、`drawnTileSource`はあるが人和専用の初回ロン状態はない。通常のロン候補・フリテン検査に人和条件を入力し、固定満貫と通常役の通常得点を候補として比較する。通常の役なしロン禁止は保つ。
- **パオ:** 副露と槓の`OpenMeld`は種類、`fromPlayerId`、鳴き牌IDを保存するが役別責任者はない。四槓子の4つ目大明槓の条件を現行履歴から判定できるか、固定テストする。和了結果に役満別個数・責任席を保持し、単一ron payerの検証を複数payerへ拡張する。責任額、本場、供託は別内訳にし、点棒保存を維持する。
- **ロンと流局:** `getRonCandidates()`は放銃者から下家、対面、上家の順で候補を列挙し、現在は宣言された全候補を和了にする。宣言集合に複数ロン・頭ハネを適用する。`abortiveDraw`に三家和を追加し、Issue #18の`settleRound()`で親維持、本場+1、局据置、供託持越しを行う。
- **槍槓・四風連打:** `RonWindow.kind`は通常打牌・暗槓・加槓を区別し、槍槓回答後にだけ`completeKan()`が呼ばれる。槍槓候補にも通常ロンと同じ複数ロン・三家和判定を適用する。四風連打はロン回答後の`awaiting-call`側で判定されており、有効な宣言ロンを先に解決する。
- **立直・供託:** `pendingRiichi`は宣言打牌のロン回答後に成立し1,000点を差し引く。三家和確定時にpendingを無効化し、差し引かず、`depositSticks`は変えずに持ち越す。成立済み供託を手に戻さない。
- **オフライン・CPU:** オフラインは共有ゲーム関数を使い、CPUの有効ロンも同じ候補生成を使う。回答受付中は解決を保留し、頭ハネは同じ宣言集合のフィルターで行う。
- **オンラインWorker:** `advanceDecision()`は人間ロン回答を集め、`finishDecision()`は全回答後のyesを確定する。timeoutは未回答をpassにし、revision/windowを検査する。WorkerはセッションJSONを保存・再接続復元する。CPU回答も共通エンジンで処理し、回答完了後の勝敗・三家和だけをWorkerが一度確定して配信する。
- **設定・同期:** 現行`GameRules`とlocalStorageはv4。設定UI、対局開始snapshot、ホスト作成時のroom `rules_json`、オンライン再接続に設定を伝える既存基盤がある。5値を追加し、旧v1〜v4は人和・パオ・特殊形ダブル役満・三家和OFF、複数ロンONに正規化する。設定画面と確認表示、保存、オンライン入力検証・room同期、次局/再戦のsnapshotを揃える。
