# 対局中フリーズ調査（2026-10-25）

## 結論

**原因をコードと決定的なゲーム進行テストで特定しました。** 対局ロジックは19枚目・20枚目の捨て牌を内部データへ追加できますが、河レイアウト計算は19枚以上を `RangeError` で拒否します。河が18枚の状態から捨てると、状態更新後の再描画で例外が発生し、画面の後続更新が止まります。

これは今回の2事象と整合する再現可能な原因です。ただし、取得ログに操作イベントがなく、実機の例外ログもないため、当日の操作でこの経路が実際に発火したことまではログから確認できません。

## コードで確認した事実

- `src/game/discard.ts` の `discardFromPlayer` は、合法な牌を手牌から除き、`river` と `discardHistory` に追加します。枚数上限の判定はありません（7–20行）。オンライン打牌受付もこの共通処理を呼びます（36–44行）。
- 河の内部配列 `river` と、鳴かれて河から移動した牌を保持する `discardHistory` は別管理です。鳴きでは対象牌を `river` から取り除き、履歴は維持します（`src/game/calls.ts` 98行付近）。牌数表示・描画は `river.length` を使います。
- `src/rendering/river-layout.ts` は `MAX_DISCARDS = 18` とし、`calculateRiverLayout` が19枚以上を `RangeError` で拒否します（27–28、57–64行）。これは描画側の6列×3段の制約で、ゲームロジックの上限ではありません。
- オフラインは `GameController.confirm` が先に新しいゲーム状態を設定して選択を消し、その後 `onChange` で描画します（`src/ui/controller.ts` 50–55行）。描画は自分の手牌を更新してから河レイアウトを計算するため（`src/rendering/table.ts` 90–95、115–121行）、19枚目では手牌DOM更新後、河のDOM置換や操作パネル更新の前に例外になります（`src/main.ts` 45–64行）。モデル上の打牌は済んでいる一方、画面の一部は古い状態のままになります。再度の打牌は既に打牌可能な手番でないため進みません。
- オンラインはクライアントから送った打牌を `applyOnlineGameAction` が受け、共通の打牌処理で状態を更新します（`src/online/game-engine.ts` 362–372行）。Durable Objectは正常終了した状態を保存・配信します（`worker/room.ts` 970–987行）。クライアントの描画は手牌・副露の更新後に河を処理し（`src/online/game-controller.ts` の `render` / `renderRivers`、419–430行）、ここでも19枚以上のレイアウト計算が例外になります。オンライン側も受信状態の一部を描画した後で止まる経路があります。
- 王牌は14枚を保持し、通常山が空でも最終ツモ後の打牌を許可します。流局への移行は空の山から次のツモが要求された時です（`src/game/draw.ts` 12–17行、`src/game/turn.ts` 19–23行）。`discard.ts` は最終打牌かを記録します（38–44行）。河の18枚数で流局する処理はありません。
- リーチは宣言牌IDの装飾・参照に使います。鳴かれた牌は河から外れ履歴に残ります。いずれも19枚目の打牌受付に上限を追加しません。
- 診断ログの `page_resumed` は `visibilitychange` 後の復帰記録であり、河描画例外や打牌結果を示すイベントではありません。示されたログだけから直接原因は分かりません。

## 原因と未確認事項

- **特定した原因:** 18枚の次の打牌自体ではなく、19枚目を含む状態を描画する際に `calculateRiverLayout` が例外を投げることです。ゲーム状態は先に更新されているため、打牌を巻き戻す処理や画面の後続更新には到達しません。
- **オフライン事象との一致:** 手牌DOMから牌が消えた後に河描画で停止し、古い河・選択表示が残る順序をコードで確認しました。
- **オンライン事象との一致:** サーバーは合法打牌を受理して状態を保存できます。クライアントが19枚の河を描画する時に同じ例外が起こり、表示が18枚のまま残る順序を確認しました。報告された「右側の河18枚」がサーバー状態も18枚だったことを証明するわけではありません。
- **未確認の別仮説:** 牌ID不一致、古いrevisionによる拒否、通信切断、応答タイムアウト、手番同期ずれはコード上に個別の拒否・復旧経路がありますが、提示ログには打牌の送信・受信・成功・拒否イベントがなく、今回起きたかは判定できません。

## 推奨対応と影響範囲

次の修正作業では、ゲーム内部の河を18枚で打ち切らずに、6列×3段を超える河を安全に描画できるレイアウト仕様を決め、オフライン・オンライン共通の描画で扱う方法を検討してください。描画例外を境に打牌状態とUI状態が分断されない確認も必要です。ゲーム本体の修正は今回行っていません。
