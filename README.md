# Quill Mahjong

日本式リーチ麻雀のStep 12（点棒管理・局進行）。4人が25,000点で東1局を開始し、和了・流局の精算から連荘・親交代、東風戦の最終順位まで進めます。Step 11の符・点数計算、ロン／見逃す、CPU自動和了、ダブロン・トリプルロンを維持しています。以下の過去Step節は当時の実装・実機確認の記録で、現在の仕様は末尾のStep 12を参照してください。

## 操作と画面

既存の4人卓、牌モデル、牌山生成・シャッフル・配牌、SVG牌デザイン、開発用牌一覧を維持しています。開始時の親は自分で、以降は局結果によって交代します。各局の親は配牌直後に13枚＋右端の追加牌1枚から、ツモなしで打牌します。以降は生きた牌山の先頭から1枚ツモし、14枚から1枚打牌します。

自分の牌をタップすると物理牌IDで選択します。別の牌で選択変更、同じ牌で解除し、「打牌する」で確定する2段階操作です。選択だけではGameStateを変更しません。通常ツモ後に和了条件を満たせば「ツモ和了」も選択できます。TabとEnter／Spaceでも操作できます。ツモ牌は右端に間隔を空け、自分の打牌直後は13枚、CPU進行中は操作を無効にします。

CPUはそれぞれ自動的にツモ・打牌し、各打牌の前に300ms待ちます。CPU3の打牌後は自分が自動的にツモし、次の選択ができます。現在の手番は席の強調表示と中央情報で示します。左右（CPU1・CPU3）と対面（CPU2）の裏向き手牌表示を削除し、名前・自風・持ち点・親・手番を表示します。対局中は和了者以外のCPUの牌面・物理牌IDをDOMに出しません。流局後の結果欄ではテンパイ確認のため4人の手牌を公開します。

河の牌SVGは、自分0°、右CPU1 270°、対面CPU2 180°、左CPU3 90°にCSSで回転します。内部配列とDOMは打牌順を維持し、描画時に各牌のgridRow/gridColumnだけを席に合わせて変換します。席視点で6枚ずつ左上から右へ、次の段へ進む配置を回転した結果、画面上では上下6列×3行、左右3列×6行になります。右は左下から上へ進み、6枚ごとに右の列へ、左は右上から下へ進み、6枚ごとに左の列へ、対面は右下から左へ進み、6枚ごとに上の段へ進みます。空の状態から18枚分を確保し、河の内部スクロールは使いません。

河のSVGは幅20〜24px（375px幅では約20.25px）で、左右の牌は縦横を入れ替えたセルに収めます。CPU手牌の削除と横向き牌による高さ圧縮で、下部操作に余裕を作りました。打牌操作エリアは通常の文書配置を保ったposition:sticky / bottom:0で下端に追従し、12px＋safe-area-inset-bottomの内側余白を確保します。ページ下端にも16px＋セーフエリアの余白があります。高さ不足時はページ全体を縦スクロールでき、手牌と操作を一緒に表示できます。手牌14枚の1行表示と44px以上の打牌ボタンを維持しています。

中央には実際の生きた牌山枚数・王牌枚数・手番を表示します。未管理の局数・点数は表示しません。

## 状態と純粋なゲーム処理

`src/model/game.ts`の既存GameStateを再利用し、phaseを以下の3状態にしました。

- `awaiting-draw`：turnPlayerIdのプレイヤーがツモ待ち。
- `awaiting-discard`：同じプレイヤーが13枚＋drawnTile1枚で打牌待ち。配牌直後もこの状態。
- `won`：自分のツモ和了宣言で停止。和了結果と14枚を維持。
- `wall-exhausted`：次のツモ時に生きた牌山が空だったため停止。turnPlayerIdはツモできなかったプレイヤー。

`src/game/turn.ts`が順序とツモ待ちの検証・牌山終了を担当します。`draw.ts`の`drawTile()`は現在手番・ツモ待ち・hand13枚・drawnTile=null・生きた牌山ありを要求し、先頭牌をdrawnTileへ移動します。handと王牌は変えません。不正操作と空の牌山への直接ツモはRangeErrorです。`drawOrStop()`は正しいツモ待ちで牌山が空なら停止へ遷移します。

`discard.ts`の`discardFromPlayer()`を共用し、`discardTile()`を全員・全巡に拡張しました。現在手番・打牌待ち・13枚＋追加牌を要求し、指定された物理牌IDの牌を本人の河の末尾へ移します。handから捨てた場合はツモ牌をhandに取り込み、ツモ牌を捨てた場合はhandを維持します。結果はhand13枚・drawnTile=null、次のプレイヤーのツモ待ちです。手番違い・連続打牌・不明ID・不正な手牌・停止後の操作は拒否します。

状態更新はDOM非依存の純粋関数です。元のGameStateや配列・物理牌を変更せず、既存の物理牌を移動するので赤5と同牌種のIDを保存します。

## CPUと自動進行

`src/game/cpu.ts`の`chooseRandomDiscard()`はhand13枚とdrawnTile1枚の14候補から等確率で1枚のIDを選びます。乱数源を注入でき、範囲外・非有限値は拒否します。手牌評価は行いません。`DiscardStrategy`として独立しているので、将来のCPU思考に差し替えられます。

`src/game/automatic-turns.ts`の`AutomaticTurnRunner`は、純粋なツモ・打牌処理を呼び、CPUの待機を制御します。乱数源・選択戦略・待機関数を注入でき、テストでは時間待ちを省略できます。実行中の再起動は拒否し、AbortControllerと世代番号で古い処理を無効にします。標準待機はキャンセル時にタイマーを解除します。キャンセルを無視する待機関数でも、await後の世代検証によって古い状態を反映しません。古い処理のfinallyも新しい実行を解除しません。

`src/ui/controller.ts`のGameControllerが現在のGameStateと選択IDを保持します。確定時に同期的に1枚だけ打牌し、選択を消して自動進行を開始します。進行中の選択・確定を拒否するので連打でも複数枚動きません。「新しい対局」は進行をキャンセルして再配牌し、河・選択・手番・牌山を初期化します。`src/rendering/table.ts`がDOM描画、`src/main.ts`が操作と描画通知の接続を担当します。

## 牌山終了

通常ツモに使うのは生きた牌山だけです。最後の1枚をツモしたプレイヤーは通常どおり打牌でき、その次のツモが必要になった時点で「牌山がなくなりました」と表示し停止します。王牌14枚は使用せず、停止後のツモ・打牌・CPU進行は禁止します。「新しい対局」は利用できます。標準の配牌では追加ツモ69回・打牌70回で停止します。

## Step 6：和了形判定エンジン

`src/analysis/winning-shape.ts`は門前の14枚について通常形（4面子1雀頭）、七対子、国士無双を判定する純粋関数です。役なしでも形として成立します。Step 8ではStep 7の役判定を経由して、自分のツモ和了処理に接続します。DOM・SVG・GameState・物理牌IDに依存せず、入力配列と牌を変更しません。赤5は既存の`tileKindKey()`で通常の5と統合します。

```ts
import { analyzeWinningShapes, isWinningShape } from './src/analysis/winning-shape.ts';
import { ordinaryTile } from './src/model/tile.ts';
import type { Tile } from './src/model/tile.ts';

const tiles: readonly Tile[] = [1, 2, 3, 4, 5, 6, 7].flatMap(rank => [
  ordinaryTile({ category: 'suited', suit: 'man', rank: rank as 1 | 2 | 3 | 4 | 5 | 6 | 7 }),
  ordinaryTile({ category: 'suited', suit: 'man', rank: rank as 1 | 2 | 3 | 4 | 5 | 6 | 7 }),
]);
const analysis = analyzeWinningShapes(tiles);
console.log(isWinningShape(tiles)); // true
console.log(analysis.standard.decompositions.length); // 3
console.log(analysis.sevenPairs.isWinning); // true
```

`WinningShapeAnalysis`は全体の`isWinning`、`standard`の成立フラグと全`decompositions`、`sevenPairs`の成立フラグと7種類の`pairs`、`thirteenOrphans`の成立フラグと重複牌種`duplicate`を返します。特殊形の不成立時は`pairs`／`duplicate`が`null`です。通常形の各分解は`pair: TileKind`と4面子の`melds`を保持します。面子は`type: 'sequence'`と連続3種類の`tiles`、または`type: 'triplet'`と`tile: TileKind`の判別可能な型です。返却する牌種に赤属性や物理IDはありません。

通常形は34種類のカウントを作り、2枚以上ある全牌種を雀頭候補にして2枚を取り除きます。残りの最小牌種から刻子と同色の順子（開始数1〜7）の両方へ再帰・バックトラックし、4面子で全牌を使い切る結果だけ採用します。字牌の順子、色をまたぐ順子、9から1への循環を認めません。雀頭と正規化した面子のキーで重複を除き、牌種順・面子種別順で結果を安定化します。同じ面子が複数必要な場合はその個数を保持し、面子を並べ替えただけの分解は追加しません。入力順によらず全分解を返し、通常形と七対子などの同時成立も保持します。

七対子は異なる7種類がそれぞれちょうど2枚ある場合のみ成立し、同種4枚を2対子にしません。国士無双は各色の1・9と字牌7種類をすべて含み、他の牌がなく、1種類だけが2枚ある場合に成立します。14枚制約の下で13種類を揃えることで重複が1組であることを保証します。

型は`readonly Tile[]`で牌の種類と赤5の制約を表し、JavaScript等からの不正入力は実行時にも検証します。14枚以外、同牌種5枚以上、未知の牌種、型に反する牌面・赤属性は`RangeError`です。正常な14枚の不成立はエラーにしません。将来はPlayerStateのhandとdrawnTileから牌面だけを取得する薄い変換処理で接続できます。

固定テストでは各面子構成、字牌、4枚使用、赤5、七対子、国士無双、複数分解・同時成立、不正順子、入力拒否、凍結入力・不変性・順序安定性を検証します。固定乱数の合法な14枚1000手を独立した判定オラクルと比較し、面子から生成した合法な成立手500手では成立と全分解の牌数一致・順子妥当性・重複排除を確認します。

Step 6の形判定API自体は役・和了方法を扱いません。基本役と和了方法の評価はStep 7の独立APIを使用します。未実装：テンパイ、待ち牌の探索、シャンテン数、ドラ・赤ドラの翻数、和了宣言・ボタン、点数・符、鳴き・カン、リーチ、CPU手牌評価。国士無双十三面待ちや和了牌の取得元も判定しません。和了形成立は、役を満たして実際に和了できることとは別です。

## Step 7：基本役判定エンジン

`src/analysis/yaku.ts`の`analyzeYaku(tiles: readonly Tile[], context: WinningContext): YakuAnalysis`は、Step 6の`analyzeWinningShapes()`の検証・返却分解を利用する純粋関数です。GameStateから情報を取得せず、入力配列・牌・コンテキストを変更しません。Step 8では薄いゲーム処理を通して自分のツモ和了と画面に接続します。

| 対応役 | 翻数／役満 |
| --- | --- |
| 門前清自摸和 | 1翻（ツモのみ） |
| 断么九 | 1翻 |
| 役牌：白・發・中・自風・場風 | 該当条件ごとに1翻 |
| 平和 | 1翻 |
| 一盃口 | 1翻 |
| 七対子 | 2翻 |
| 対々和 | 2翻 |
| 国士無双 | 1役満 |

```ts
import { analyzeYaku } from './src/analysis/yaku.ts';
import { ordinaryTile } from './src/model/tile.ts';
import type { Rank } from './src/model/tile.ts';

const tiles = ([1, 2, 3, 4, 5, 6, 7] as Rank[]).flatMap(rank => [
  ordinaryTile({ category: 'suited', suit: 'man', rank }),
  ordinaryTile({ category: 'suited', suit: 'man', rank }),
]);
const result = analyzeYaku(tiles, {
  winMethod: 'ron',
  winningTile: { category: 'suited', suit: 'man', rank: 4 },
  seatWind: 'east',
  roundWind: 'south',
});
console.log(result.isWinningShape); // true（形としての成立）
console.log(result.hasSupportedYaku); // true（今回対応した役がある候補の存在）
console.log(result.candidates.length); // 4（通常形3候補と七対子1候補）
```

`WinningContext`は`winMethod: 'tsumo' | 'ron'`、完成14枚に含まれる`winningTile: TileKind`、`seatWind`（自風）、`roundWind`（場風）を必須とします。風は`east / south / west / north`です。赤5と通常5は同じ牌種です。任意の`isClosed?: true`は省略時も門前を意味し、開いた手牌を渡す`false`は拒否します。鳴き対応は将来別途追加する必要があります。

返却値は`isWinningShape`、`hasSupportedYaku`、`candidates`です。候補は安定した`id`、`shape: standard / seven-pairs / thirteen-orphans`、成立役`yaku`（安定ID、`han`、`yakuman`）、通常翻合計`totalHan`、役満数`yakumanCount`を持ちます。通常形には`decompositionId`、Step 6の`decomposition`、和了牌の`assignment`（雀頭、または0始まりの`meldIndex`と`tileIndex`）、`wait`を保存します。刻子の`tileIndex: 0`は同種3枚の代表位置です。七対子は`pairs`、和了対子の`pairIndex`、`wait: tanki`、国士無双は`duplicate`と`assignment / wait: null`を返します。

平和は全4面子が順子、雀頭が役牌以外、和了した順子が両面待ちの場合だけ成立します。和了牌を含む雀頭・各面子を割り当て候補として列挙し、中央牌は`kanchan`（嵌張）、123の3と789の7は`penchan`（辺張）、その他の順子端は`ryanmen`（両面）とします。23→1の123と78→9の789は両面です。雀頭は`tanki`（単騎）、刻子は`shanpon`（双碰）とし、平和を付けません。同じ牌種が雀頭や複数の順子にある場合は割り当てごとに評価します。

役牌は通常形の刻子のみです。雀頭は役牌役を生みません。自風と場風は別ID（`yakuhai-seat-wind` / `yakuhai-round-wind`）で、東場・東家の東刻子は2翻です。白・發・中も個別IDで加算します。平和では三元牌・自風・場風の雀頭を拒否し、それ以外の風牌雀頭を認めます。

各分解・各割り当ての役は独立し、異なる候補の役を合算しません。通常形はStep 6の安定した分解順、割り当ては雀頭→面子順、最後に七対子→国士無双の順です。同一分解の同一面子が複数ある場合、対称な割り当ては最初の面子位置を代表にして重複を除きます。`11223344556677m`の七対子候補に通常形の平和・一盃口・対々和・役牌刻子を混ぜません。一盃口は重複順子が何組あっても1翻のみです。二盃口が成立する特殊ケースでも、Step 7の判定対象は一盃口のみで、二盃口は未実装です。

国士無双は`han: 0 / yakuman: 1`、候補は`totalHan: 0 / yakumanCount: 1`です。13翻として計上せず、ツモ等の通常役も合算しません。十三面待ちによるダブル役満は扱いません。符・点数未実装のため最終得点・最高得点候補は決定しません。

14枚以外、牌種5枚以上、不正な牌、存在しない和了牌、不正な和了牌種・風・和了方法・開いた手牌指定は`RangeError`で拒否します。正常な不成立手牌は両フラグがfalse、候補なしです。形成立でも今回の役がゼロなら`hasSupportedYaku: false`ですが、未対応役があるため実際の役なし・和了不可を保証しません。

固定テストは役ごとの成立・不成立、全待ち方、役牌雀頭と風の組合せ、同一分解の複数割り当て、通常形と七対子の同時成立、異なる分解での役の分離、役満分離、入力拒否、凍結入力・順序安定・重複排除を確認します。既存59件を維持しています。

未対応：立直・ダブル立直、一発、海底・河底、三色同順・一気通貫、混全帯么九・純全帯么九、混一色・清一色、二盃口、三暗刻・三槓子、小三元・混老頭、その他役満、ドラ・赤ドラ、符・点数、フリテン、鳴き・カン、和了処理・宣言UI・CPU和了宣言、リーチ・テンパイ・シャンテン判定。未対応役を成立扱いにしません。Step 7 API自体は和了処理を行わず、Step 8のゲーム層で宣言条件を検証します。

## Step 8：自分のツモ和了と対局終了

`src/game/tsumo.ts`の純粋関数`canDeclareTsumo(game, playerId)`と`declareTsumo(game, playerId)`を追加しました。対象はPlayerId=0・human・自分の手番・門前のみです。`phase: awaiting-discard`で手牌13枚＋実際に生きた牌山から取得した`drawnTile`1枚があり、Step 7の`analyzeYaku()`が和了形と対応役を認める場合に宣言できます。終了済み・不正な牌数・存在しないプレイヤー等は不可で、宣言関数は`RangeError`を投げます。最終生牌を引いた直後も宣言可能です。壁の空判定は次のツモ時に行う既存仕様を維持します。

## Step 8.2：ドラ表示牌と通常ドラ

## Step 10：ロン和了・フリテン・同時ロン

### 成立条件と共通判定

正式な打牌直後の最新の捨て牌について、放銃者以外の13枚の手牌へその牌を加え、14枚の和了形と対応役（または役満）が成立し、フリテンでなければロンできます。自分自身の捨て牌、過去の捨て牌、前の対局の牌、宣言／見逃し済みの打牌では宣言できません。ドラだけでは和了できません。

`src/game/win.ts` の `evaluateWin()` と `selectWinCandidate()` をツモ／ロンで共通利用します。既存の `analyzeYaku()` に `winMethod: 'ron'`、捨て牌の牌面、和了者自身の自風、東の場風を渡します。ロンに門前清自摸和は付きません。断么九・役牌・平和・一盃口・七対子・対々和・国士無双は既存エンジンの成立条件を使い、新しい役は追加していません。既存の `selectTsumoCandidate()` と `ROUND_WIND` のexportは維持しています。

### APIと打牌直後の解決

DOM非依存の純粋関数は `src/game/ron.ts` にあります。

- `canDeclareRon(game, playerId)`：現在の打牌に対するロン可能性。
- `getRonCandidates(game)`：放銃者の次の席から順に、役・ドラ・翻数を独立評価した候補を返す。
- `declareRon(game, playerId)`：人間の宣言とCPU全員の自動宣言を一括確定する。
- `passRon(game, playerId)`：人間の見逃しを記録し、CPUのロンまたは次のツモ待ちへ進む。
- `resolveDiscardRon(game)`：各打牌後に共通の解決を行う。
- `getRonTile(game)`：現在の宣言待ちと河の最新物理牌IDを検証する。
- `getWaitingTileKinds(hand)`／`isDiscardFuriten(player)`：和了形の待ち牌全体と河によるフリテンを計算する。

`discardTile()` は牌を河へ移した後、`phase: 'awaiting-ron'` と `ronWindow: { discarderId, tileId }` を作り、他の3席を評価します。候補なしなら従来どおり次席の `awaiting-draw`、CPUだけなら即座に `won` となります。人間も候補ならCPU候補の権利を保持したまま入力を待ちます。候補結果を別のstateへ重複保存せず、現在の不変な手牌・河・表示牌から評価します。待機中の手番IDは放銃者を指します。解決時にwindowを消し、続行時だけ次席へ進めます。

人間は専用の「ロン和了」「見逃す」を操作します。通常のツモ和了ボタンとは別です。見逃してもCPUのロンは取り消しません。CPU候補は必ず全員ロンし、頭ハネはありません。ダブロン／トリプルロンを認め、三家和による途中流局は採用していません。人間入力待ちの間、CPUが先に和了を確定したり次のツモへ進んだりしません。途中状態からのCPU単独 `declareRon()` は人間の選択が未解決ならRangeErrorとなり、CPUの宣言は共通解決関数で扱います。

CPUの自分のツモではStep 9どおりツモ和了を打牌より優先します。打牌した場合だけロン評価を行います。`AutomaticTurnRunner` は宣言待ちで停止し、見逃し後に続行する場合はcontrollerから再開します。300ms待機・AbortController・世代番号による古い非同期処理の取消を維持しています。和了後はrunnerの `running` がfalseとなり追加のツモ・打牌・宣言を行いません。純粋APIは不正な状態遷移をRangeErrorで拒否します。

### フリテン

河によるフリテンは現在の13枚に34牌種をそれぞれ追加して `isWinningShape()` で求めます。役の有無を条件にせず、和了形が完成する待ち牌全体と自分の河を照合します。両面の一方を捨てていればもう一方でもロンできません。通常5と赤5は同じ牌種です。手牌に4枚ある牌種の5枚目は待ちに含めません。七対子・国士無双の待ちにも対応します。河フリテンは保存したflagではなく、現在の手牌から毎回計算します。

人間がロン可能な牌を見逃したときだけ `PlayerState.temporaryFuriten` をtrueにします。他家のツモ・打牌では解除せず、自分が生きた牌山から正常にツモした時点でfalseにします。失敗ツモや牌山切れでは解除しません。河のフリテンは別に残ります。どちらもツモ和了を妨げません。新しい対局は全席false、windowと結果nullに初期化します。リーチ後の恒久フリテンは今回対象外です。

### 結果・物理牌・ドラ

`GameState.winResult` は `TsumoResult | RonResult | null` の判別可能unionです。ツモ結果の意味と既存フィールドは維持し、共通項目を `WinDetails` に抽出しました。ロン結果は和了方法・放銃者・和了物理牌IDと、各勝者の `RonCandidate` 配列を持ちます。勝者ごとに対応役、役翻数、通常ドラ／赤ドラ枚数と加算翻数、合計翻数、役満数を独立保存します。

ロン牌は放銃者の河に保持し、和了者の手牌へ移したり複製したりしません。画面は各勝者の13枚と、河からIDで参照した同じロン牌を右端に分離して14枚表示します。同時ロンでもstateの物理牌は136枚、各牌種4枚、赤5各色1枚、ID一意、王牌14枚を維持します。全勝者を放銃者の次の席から表示し、和了したCPUだけ手牌を公開します。他のCPUと非公開王牌はDOMへ出しません。

### モデルと精算API

`src/model/match.ts`の`MatchState`は、4人の`points`、東固定の`roundWind`、`roundNumber`、`dealerId`、`honba`、`depositSticks`、現在の`game`、`lastSettlement`、`status`（playing／round-ended／match-ended）を保持します。牌・手番・ロン待ち・和了結果は既存`GameState`のみに保持し、`GameController.game`は`match.game`への互換アクセサです。持ち点をGameStateへ複製しません。現在の親は配牌時に一致させ、精算時にもMatchStateとGameStateの一致を検証します。

`src/game/match.ts`の純粋API：

- `startMatch(game?)`：25,000点×4の対局を開始。
- `updateMatchGame(match, game)`：現在局を更新し、確定した和了／流局を精算。
- `settleRound(match)`：進行中→局終了／対局終了の一方向遷移。一度精算済みなら同じ状態を返す。
- `nextRound(match, create?)`：精算済み局のみ次局へ。持ち点・供託を維持し、136枚の新しい牌山から王牌14枚・親からの配牌・自風を生成。
- `rankPlayers(match)`：最終順位を算出。
- `assertPointConservation(match)`：整数残高と点棒保存則を検証。

点棒精算はStep 11の`ScoreResult.payments`をそのまま使用します。符・基本点・支払額を再計算しません。支払者から和了者へ移動し、同時ロンは各勝者のpaymentsを独立して合算します。重複勝者・重複支払者、勝者自身からの支払い、不正金額、支払い合計の不一致を拒否します。

`RoundSettlement`は終了理由・局番号・親・本場、精算前後の持ち点、支払者／受取者・基本点／本場／ノーテン罰符を分離した支払い記録、供託受取、4人のテンパイ、各収支、次局情報、対局終了フラグを保存します。結果・配列・支払い・次局情報をObject.freezeし、描画は保存済み結果だけを読みます。最終受取額はpaymentsのpointsと供託配分に記録し、収支を結果欄に表示します。`ScoreResult.totalPoints`は本場を含まない基本の獲得点数のままです。

## Step 13.1：自分の基本リーチ

自分（PlayerId 0）のみ、進行中の対局で自分の打牌手番、門前、未リーチ、手牌13枚＋ツモ牌1枚、持ち点1,000点以上、生きた牌山4枚以上を満たすときに宣言できます。王牌14枚は残り枚数に含めません。親の配牌直後の第一打も対象です。現在の全手牌は門前で、門前判定は `isClosedForRiichi()` に分離しています。

`src/game/riichi.ts` のDOM非依存API：

- `getRiichiDiscardOptions(game, playerId, points)`：物理牌ID順で候補を列挙。各候補は `tileId`、`waitingTileKinds`、`waitKindCount` を保持します。
- `canDeclareRiichi(game, playerId, tileId, points)`：選択した物理牌の可否を確認します。
- `declareRiichi(match, playerId, tileId)`：自分のみ宣言し、新しいMatchStateを返す純粋な状態遷移です。不正操作はRangeErrorで入力状態を変更しません。

14枚から選択した物理IDの牌だけを除き、残り13枚に既存の `getWaitingTileKinds()` を適用します。待ちが1種類以上なら役なしテンパイでも候補になります。赤5・通常5は同じ牌種で解析し、打牌は別々の物理IDで扱います。符・点数・和了形解析を再実装していません。

牌を選択すると、宣言可能な場合に「リーチ」が有効になります。宣言不可の選択では同じボタンを無効にします。「打牌する」は従来どおりリーチなしの打牌です。「リーチ」は宣言と打牌を同時に行います。ボタン3個は320pxでも同じ44px以上の高さの1行に収まり、手牌のサイズ・14枚横1行、河の回転・6列×3段、中央ドラ3＋2、セーフエリアを維持します。ロン待ちやリーチ成立後はリーチボタンを非表示にします。

## Step 13.2.1：向聴数と有効牌によるCPU通常打牌

`calculateShanten(tiles)` は門前13枚を入力とする純粋関数です。テンパイは0向聴、テンパイまであと1段階は1向聴です。一般形・七対子・国士無双を個別に返し、その最小値を手牌全体の向聴数とします。枚数違い、不正な牌、同種5枚以上を拒否し、入力を変更しません。既存の `Tile` / `TILE_KINDS` / `tileKindKey()` を使用し、赤5と通常5は同種です。

一般形は34種の枚数配列を3色と字牌に分け、刻子・順子・雀頭・対子搭子・隣接搭子（両面/辺張）・1枚間隔搭子（嵌張）・孤立牌の**すべての分解候補**を探索します。各部分を面子数・搭子数・雀頭有無の組に集約して組み合わせ、`8 − 2×面子数 − min(搭子数, 4−面子数) − 雀頭有無` の最小値を取ります。重複する順子/刻子や雀頭候補も探索します。面子4組・雀頭1組の上限と搭子上限で枝を制限します。七対子は `6 − 対子種類数 + max(0, 7−異なる牌種数)`、国士無双は `13 − 么九字牌の種類数 − 対子有無` です。同種4枚は七対子の対子1種類です。

CPUは所有する14枚の**物理ID**を候補として、打牌後の13枚を評価します。比較順は、①最小向聴数が小さい、②有効牌の見込み残り枚数が多い、③有効牌種類数が多い、④赤5を捨てない、⑤物理ID昇順です。同一入力の結果は固定で、最終同点に乱数を使いません。同種の打牌評価を共用しても物理IDと赤牌属性は保持します。

有効牌は、仮想ツモ後に最適な次の打牌を行うことで向聴数が減る牌種です。0向聴の場合は既存 `isWinningShape()` で和了形を完成する牌種を調べます。打牌後に既に4枚ある牌種の仮想5枚目は除外します。各有効牌の見込み枚数は4枚から**自分の手牌＋ツモ牌、4人の河、公開ドラ表示牌**を引きます。候補の打牌は河に移っても見えるので、元の14枚を差し引いたままです。赤5と通常5は合算し、物理IDを重複カウントしません。公開済み4枚により残り0枚の有効牌も種類として区別し、見込み枚数には0を加えます。理論上0向聴でも実際の和了牌が残っていない場合があり、向聴数と実際の待ち・リーチ成立条件を混同しません。

戦略の純粋関数には自分の14枚と公開牌だけを渡します。他家の手牌、未公開の生きた牌山の配列、非公開の王牌、実際の次ツモは参照しません。公開ドラを取り出す既存関数だけを境界で呼びます。非公開牌の交換や牌山の並べ替えでも選択が変わらないことをテストしています。

自動進行の優先順位は **ツモ和了 → リーチ成立済みならツモ切り → 既存条件を満たすリーチ → 向聴数戦略の通常打牌** です。リーチ候補の「待ち種類数最大→物理ID順」は変更していません。`chooseRandomDiscard()` と `AutomaticTurnOptions.chooseDiscard(player, random)` は維持しています。旧ランダム挙動・旧マイクロタスク待機を検証するテストは明示注入で継続します。フリテン、リーチ保留、供託確定、ロン・ツモ・得点・局進行・点棒保存則の処理とUI/CSSは変更していません。

### 計算量・性能記録

34要素の枚数配列で探索し、同じ牌構成と部分分解を1手のローカルキャッシュでメモ化します。異なる物理牌でも同種打牌は1回だけ評価し、最小向聴数を達成しない候補の有効牌探索を省きます。仮想ツモのツモ切りは改善しないので次打牌探索から除外します。キャッシュは手番を越えて保持しません。自動進行は約6msの区間ごと（仮想ツモ評価の境界）に `setTimeout(0)` で制御を返します。各区間は不可分な探索の分だけ予算を超える可能性があります。計算中にDOMを更新せず、既存300ms待機を維持し、再開時にキャンセル/世代/状態変更を検査して古い計算を確定しません。

Linux / Node v24.19.0、120種類の合法な通常配牌、20手ウォームアップ後の計測（ms）。単一時間閾値によるテストにはしていません。

### 固定牌山・通常配牌の再現手順

合法な136枚固定牌山の自動テスト `tests/shanten-progression.test.ts` は、CPU1の `123m 11z 23p 45s 67s 2z 3z`（2向聴）に `4p` をツモって通常打牌後1向聴、次の `3s` で0向聴に到達し、既存のリーチ処理が宣言するシナリオです。1,000点徴収・宣言牌ID・次手ツモ切り・136枚の同一物理IDと点棒100,000点を検証します。

通常配牌はLCGの固定シード0（`tests/helpers.ts` の `seeded(0)`）で再現できます。本番へ固定シードや状態注入UIを追加していません。ブラウザテストの通信差し替えだけで `startGame(seeded(0))` を使い、通常の戦略と300ms待機を実行します。

1. 自分のツモ牌を選び「打牌する」を押すことを繰り返します（ロン可能時は「見逃す」）。
2. 初期CPU1/2/3はそれぞれ3/3/5向聴。CPU1は通常打牌1回目で2向聴、5回目で1向聴、8回目でテンパイ・リーチ、24,000点・供託1本になります。
3. CPU1の次手はツモ切り。CPU2も9回目でリーチし、供託2本になります。その後の人間打牌でCPU2のロンが成立し結果ダイアログが開きます。
4. 初期・通常打牌後・自然なリーチ・和了結果の7サイズ画像は [`docs/screenshots/step13.2.1/`](docs/screenshots/step13.2.1/) に保存しています。

通常配牌8シード（0〜7）で新旧戦略を比較しました。新戦略は各シードで1〜2CPUがテンパイ・リーチし、ランダム戦略はこの8シードではテンパイ/リーチ0でした。CPU3の自然なリーチもシード1/3/4/7で確認しています。これは固定シードでの検証結果であり、全対局でリーチを保証する仕様ではありません。比較は同じ配牌・同じ人間ツモ切り方針ですが、CPU打牌が変わるため局の終了時点や獲得ツモは変わり得ます。席ごとの向聴数推移・最小向聴数・テンパイ/リーチ席はbenchmark.jsonに記録しています。
